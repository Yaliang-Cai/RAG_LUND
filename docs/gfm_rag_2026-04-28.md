## 1. Overview

GFM-RAG (Graph Foundation Model RAG) integrates [`gfmrag`](https://github.com/rmanluo/GFM-RAG) as a new `mode="gfm"` retrieval path alongside the existing LightRAG-based paths (PPR, hybrid, auto). Instead of performing random walks (PPR) or dense/sparse vector lookup, GFM uses a pre-trained graph neural network reasoner (`G-reasoner-34M`) that reasons over the exported knowledge graph structure to retrieve the most relevant document chunks for a query.

The integration targets two use cases:

- **Standalone GFM retrieval**: `mode="gfm"` in `aquery()` — GFM is the sole retrieval engine; retrieved chunks feed directly into the LLM for answer generation.
- **GFM as a retrieval path in router mode**: the `gfm_multihop` profile registers GFM as an optional path alongside PPR and hybrid, for weighted RRF fusion. GFM is commented out in the profile by default and must be explicitly enabled.

### Key differences from PPR

| | PPR | GFM |
|---|---|---|
| Graph traversal | Personalized PageRank random walk | Learned GNN graph reasoning |
| Model | No model (algorithmic) | `G-reasoner-34M` (34M params) |
| Requires export | No | Yes (one-time offline export) |
| Requires Neo4j | At query time (live graph) | At export time only |
| Output | Chunk IDs ranked by PPR score | Chunk IDs ranked by GFM score |
| Latency | Fast (graph traversal) | Higher (GNN inference, thread pool) |
| Multi-hop | Implicit (random walk) | Explicit (learned graph reasoning) |

## 2. Architecture

```
                    ┌────────────────────────────────────┐
                    │  export_lightrag_to_gfm.py (once)  │
                    │                                    │
                    │  LightRAG KV store (chunks)        │
                    │  + Neo4j (entities, relations)     │
                    │           │                        │
                    │           ▼                        │
                    │  <data-dir>/<graph-name>/          │
                    │    processed/stage1/nodes.csv      │
                    │    processed/stage1/edges.csv      │
                    │    processed/stage1/relations.csv  │
                    │    raw/documents.json              │
                    └──────────────┬─────────────────────┘
                                   │  pre-built GFM index
                                   ▼
query                  ┌───────────────────────┐
  │                    │  GFMRetrieverWrapper   │  ← lazy singleton
  │  mode="gfm"        │  (gfmrag.GFMRetriever) │
  ├──────────────────► │  .get_instance(...)    │
  │                    │  .retrieve(query, k)   │
  │                    └──────────┬────────────┘
  │                               │ [{id, score}, ...]
  │                               ▼
  │                  ┌─────────────────────────┐
  │                  │  LightRAG KV store       │
  │                  │  text_chunks_kv          │
  │                  │  .get_by_id(chunk_id)    │
  │                  └──────────┬──────────────┘
  │                             │ [{chunk_id, content, score}, ...]
  │                             ▼
  │                  ┌─────────────────────────┐
  │                  │  Answer Generation (LLM) │
  │                  │  _generate_answer_from_  │
  │                  │  chunks()                │
  │                  └─────────────────────────┘
  │
  │  mode="auto" + profile="gfm_multihop"
  └──────────────────► RetrievalRouter
                            │
                    ┌───────┴──────────┐
                    │  parallel paths  │
                  [ppr]   [hybrid]   [gfm*]   (* uncomment in profiles.py)
                    │       │          │
                    └───────┴──────────┘
                            │ weighted RRF fusion
                            ▼
                         reranker
                            │
                         top-k chunks
                            │
                         LLM answer
```

## 3. Offline Export Pipeline

GFM-RAG uses a **pre-built index** (Path B): the knowledge graph and chunk content are exported once from LightRAG to CSV files that GFM-RAG's indexer expects. This is a one-time operation per workspace; incremental exports require re-running the script.

### 3.1 Output layout

```
<data-dir>/
└── <graph-name>/
    ├── processed/
    │   └── stage1/
    │       ├── nodes.csv       # document + entity nodes
    │       ├── edges.csv       # entity→chunk (mentioned_in) + entity→entity edges
    │       └── relations.csv   # all relation type names
    └── raw/
        └── documents.json      # {chunk_id: chunk_content}
```

### 3.2 Node and edge schema

**nodes.csv** — header: `name,type,attributes`

| name | type | attributes |
|---|---|---|
| `<chunk_id>` | `document` | `{"content": "..."}` |
| `entity_<entity_name>` | `entity` | `{"description": "..."}` |

Chunk IDs are copied verbatim from the LightRAG KV store. This **chunk ID alignment** is the key design invariant: GFM document node names equal LightRAG KV store keys, so no translation layer is needed when fetching chunk content after retrieval.

**edges.csv** — header: `source,relation,target,attributes`

| source | relation | target |
|---|---|---|
| `entity_<name>` | `mentioned_in` | `<chunk_id>` |
| `entity_<name>` | `<relation_type>` | `entity_<name>` |

**relations.csv** — header: `name,attributes`  
All unique relation types from the Neo4j graph, plus `mentioned_in` (always included).

**documents.json** — `{chunk_id: chunk_content}` flat mapping.

### 3.3 Running the export

```bash
python scripts/export_lightrag_to_gfm.py \
    --working-dir ./rag_storage/My_Graph \
    --graph-name   My_Graph \
    --data-dir     ./data \
    --workspace    My_Graph          # Neo4j workspace label (defaults to --graph-name)
    # Neo4j connection defaults to env vars: NEO4J_URI, NEO4J_USERNAME, NEO4J_PASSWORD
```

After export, set in `.env`:
```bash
GFM_DATA_DIR=./data
GFM_DATA_NAME=My_Graph
GFM_MODEL_PATH=rmanluo/G-reasoner-34M   # or a local path
```

## 4. GFMRetrieverWrapper

`raganything/retrieval/gfm_retriever.py` wraps `gfmrag.GFMRetriever` as a **lazy singleton**. The singleton is created on first use and reused for all subsequent calls within a process — this avoids reloading the 34M-parameter GNN model on every query.

### 4.1 Initialization

```python
wrapper = GFMRetrieverWrapper.get_instance(
    data_dir="./data",
    data_name="My_Graph",
    model_path="rmanluo/G-reasoner-34M",
)
```

Two guards at initialization time:
- If `data_name` is empty → `RuntimeError` (GFM is not configured)
- If `gfmrag` is not installed → `ImportError` (with install hint)

### 4.2 Retrieval

```python
chunks = await wrapper.retrieve(query, top_k=10, text_chunks_kv=lightrag.text_chunks)
# Returns: [{"chunk_id": str, "content": str, "score": float}, ...]
```

`gfmrag.GFMRetriever.retrieve()` is synchronous; it runs in a thread-pool executor via `loop.run_in_executor(None, ...)` to avoid blocking the asyncio event loop.

Post-retrieval, each returned chunk ID is resolved against `text_chunks_kv` (LightRAG's live KV store). Chunks whose IDs are no longer present in the KV store are silently skipped with a `WARNING` log.

### 4.3 Constants

| Constant | Default | Description |
|---|---|---|
| `GFM_DATA_DIR` | `"./data"` | Root data directory for the GFM-RAG index |
| `GFM_DATA_NAME` | `""` | Graph name; **empty string disables GFM path** |
| `GFM_MODEL_PATH` | `"rmanluo/G-reasoner-34M"` | HuggingFace model ID or local path |

All three are defined in `raganything/constants.py` and imported into `query.py` and `paths.py` at module load time.

## 5. Integration Points

### 5.1 `aquery(mode="gfm")` — standalone retrieval

`raganything/query.py` handles `mode="gfm"` before the standard LightRAG path:

```
aquery()
  │
  ├── mode="auto"  → RetrievalRouter (classifier + RRF + rerank)
  │
  ├── mode="gfm"   → GFMRetrieverWrapper.retrieve()
  │                   → _generate_answer_from_chunks()
  │                   → return answer (or {"answer", "trace"} if return_trace=True)
  │
  └── mode="ppr" / "hybrid" / ...  → LightRAG aquery_data()
```

No RRF fusion, no neural reranker — GFM score ordering is used directly. The LLM generates an answer from the raw GFM-retrieved chunks.

### 5.2 `run_path("gfm")` — path in router

`raganything/retrieval/paths.py` handles `"gfm"` as a special case before the `_PATH_CONFIG` lookup:

```python
if name == "gfm":
    wrapper = GFMRetrieverWrapper.get_instance(...)
    chunks = await wrapper.retrieve(query, chunk_top_k, lightrag.text_chunks)
    return chunks, latency
```

This path is activated when `gfm_multihop` profile has `"gfm"` uncommented in `paths`. The chunks then enter the normal RRF → rerank pipeline alongside PPR/hybrid chunks.

### 5.3 `gfm_multihop` profile

`raganything/retrieval/profiles.py` defines a `gfm_multihop` profile for A/B testing GFM against PPR:

```python
RetrievalProfile(
    name="gfm_multihop",
    description="Multi-hop reasoning via GFM graph + PPR walk (toggle either path below)",
    paths=[
        # "gfm",    # uncomment to enable GFM graph retrieval
        "ppr",
        "hybrid",
    ],
    rrf_weights={
        # "gfm": 1.0,   # uncomment together with path above
        "ppr":    0.8,
        "hybrid": 0.6,
    },
)
```

By default this profile runs PPR + hybrid (identical to `multihop`). Uncommenting the `"gfm"` lines adds GFM as a third path in the RRF fusion. This profile is **not reachable from `mode="auto"`** — the classifier prompt does not list it; it must be explicitly requested via `profile="gfm_multihop"`.

## 6. Retrieval Trace

### 6.1 `mode="gfm"` trace

```python
result = await rag.aquery("...", mode="gfm", return_trace=True)
# result = {
#   "answer": "...",
#   "trace": {
#     "mode": "gfm",
#     "chunks_retrieved": 8,
#   }
# }
```

The GFM trace is intentionally minimal: the GFM model does not expose per-path breakdowns or confidence scores beyond chunk-level relevance scores. Use `--trace` in `query_gfm.py` to print the full trace JSON.

### 6.2 `mode="auto"` + `profile="gfm_multihop"` trace

When GFM is enabled in the `gfm_multihop` profile and called via `mode="auto"`, it appears inside the standard routing trace:

```json

  "chunks_after_rerank": 12,

    "classifier": 0.0,
    "gfm": 1.43,

}
```

## 7. Usage

### 7.1 Python API

```python
# Standalone GFM retrieval
answer = await rag.aquery(
    "How did the network partition in region A cause service B to fail?",
    mode="gfm",
)

# With trace
result = await rag.aquery("...", mode="gfm", return_trace=True)
answer = result["answer"]
n_chunks = result["trace"]["chunks_retrieved"]

# Control retrieval depth
answer = await rag.aquery("...", mode="gfm", chunk_top_k=15)

# Auto routing with gfm_multihop profile (bypasses classifier)
# Requires "gfm" uncommented in profiles.py → gfm_multihop
answer = await rag.aquery("...", mode="auto", profile="gfm_multihop")
```

### 7.2 Service Layer (`LocalRagService`)

```python
response = await service.query_with_trace(
    workspace_id="My_Graph",
    query="Compare the indexing strategies of LightRAG and HippoRAG2.",
    mode="gfm",
    chunk_top_k=10,
)
n_chunks = response["trace"]["chunks_retrieved"]
```

### 7.3 CLI (`scripts/query_gfm.py`)

```bash
# GFM standalone (primary use case)
python scripts/query_gfm.py \
    -w My_Graph \
    -q "How did event A lead to system B failing?" \
```

## 8. Enabling GFM in `gfm_multihop` Profile

To use GFM inside the RRF fusion pipeline (A/B testing against PPR):

1. Open `rag-anything/raganything/retrieval/profiles.py`
2. In the `gfm_multihop` profile, uncomment the two `"gfm"` lines:

```python
RetrievalProfile(
    name="gfm_multihop",
    paths=[
        "gfm",      # ← uncommented
        "ppr",
        "hybrid",
    ],
    rrf_weights={
        "gfm": 1.0, # ← uncommented
        "ppr":    0.8,
        "hybrid": 0.6,
    },
)
```

3. Optionally comment out `"ppr"` / `"ppr": 0.8` for a pure GFM vs. hybrid ablation.

The `gfm_multihop` profile is accessible via:
- `aquery(mode="auto", profile="gfm_multihop")` — bypasses classifier
- `run_path("gfm", ...)` — directly, for test scripts

It is **not** reachable from unguided `mode="auto"` (classifier does not list it).

## 9. Methodology (Paper Section)

### 9.1 Motivation

PPR-based retrieval (Section V3) uses graph topology to propagate relevance via random walks. It is effective at surfacing chunks connected to recognized entity seeds but is constrained by the random walk's inability to model query semantics in the graph traversal itself: the walk follows edge weights that encode graph structure, not query intent. For queries requiring complex multi-hop reasoning — where the correct retrieval path depends on understanding *which* relations are relevant to the query — a learned graph reasoner can outperform topology-only methods.

GFM-RAG addresses this by replacing the algorithmic random walk with a pre-trained Graph Foundation Model that reasons over the graph structure conditioned on the query.

### 9.2 GFM Graph Reasoning

GFM-RAG (Luo et al.) trains a graph neural network (`G-reasoner`) on a diverse set of knowledge graph reasoning tasks. At query time, the model takes the query and the exported knowledge graph as input and produces a ranked list of document nodes (chunks) that are most relevant to answering the query. Because the model is trained on multi-hop reasoning tasks, it learns to follow implicit relation chains that connect query-relevant entities to supporting document chunks, even when those chains span multiple hops that a random walk might assign low probability.

The exported graph used by GFM contains two node types — `document` nodes (one per chunk, named by chunk ID) and `entity` nodes (prefixed `entity_`) — and two edge types: `mentioned_in` edges (entity → document) and entity-to-entity relation edges from the LightRAG/Neo4j KG. This bipartite-like structure allows G-reasoner to combine entity-level relational reasoning with document-level relevance scoring in a single forward pass.

### 9.3 Chunk ID Alignment

A critical design invariant is that GFM document node names equal LightRAG KV store chunk IDs verbatim. This is enforced at export time (`write_nodes_csv` uses `chunk_id` as the node name directly). As a result, GFM's output chunk IDs can be looked up in `text_chunks_kv` without a translation layer, keeping the retrieval pipeline stateless with respect to ID mapping.

### 9.4 Async Integration

`gfmrag.GFMRetriever.retrieve()` is a synchronous, CPU/GPU-bound call. It is wrapped in `asyncio.get_event_loop().run_in_executor(None, ...)` to run in the default thread-pool executor, preventing it from blocking the asyncio event loop during concurrent queries. The singleton pattern (`_instance`) ensures the model is loaded once per process rather than on every query.

### 9.5 GFM vs. PPR: Design Trade-offs

| Dimension | GFM | PPR |
|---|---|---|
| **Query semantics** | Encoded in GNN forward pass | Encoded in entity seed selection (recognition memory) |
| **Graph structure use** | Learned relational patterns | Topology-weighted random walk |
| **Model dependency** | Requires `gfmrag` + `G-reasoner-34M` | No model (algorithmic) |
| **Offline setup** | Export required (one-time) | None (live Neo4j query) |
| **Incremental update** | Requires re-export | Live |
| **Latency** | Higher (GNN inference) | Lower (graph traversal) |
| **Multi-hop depth** | Learned, unbounded | Controlled by damping factor |

GFM is expected to outperform PPR on queries requiring learned relational reasoning (e.g. implicit causal chains, relation composition). PPR is expected to outperform GFM on queries with strong entity seeds and short hop distances, where the random walk converges quickly.

The `gfm_multihop` profile provides a controlled A/B setup: by toggling `"gfm"` in/out of the path list, the RRF fusion can be evaluated with and without GFM contribution while keeping PPR and hybrid constant.
